# 第一次把大模型跑在自己电脑上：llama.cpp 实录与 vLLM 部署笔记

今天折腾本地模型，我问得最多的一句是「这个是什么？」。CUDA 是什么，GGUF 里面到底装了什么，为什么我下载解压以后只有三个 DLL，还有模型都训练好了，怎么每问一句还得让显卡重新算？

这些问题听着挺基础，但我真正动手的时候，卡住的恰好就是这些地方。最后跑通的是 **Windows 上的 llama.cpp + Qwen3.5-4B**，用的是我这台电脑上的 **RTX 5060，8 GB 显存**。vLLM 也做了选型和部署准备，这次先把 llama.cpp 跑起来，vLLM 留作下一轮实测。

## 起因：想让项目多一个本地模型入口

我的项目原来走第三方 API。后端把问题和对话历史放进 `messages`，发给模型服务，再把答案展示在终端里。项目还有个 `callback_memory` 工具，模型遇到依赖历史的问题时，可以让后端去 PostgreSQL 召回相关记忆。

我想保留原来的 API，同时加一个 llama.cpp 入口，按需要切换。做到最后才发现，项目接入这部分其实挺直观。llama.cpp 可以在本机提供 OpenAI 兼容接口，后端还是发 `messages`，只是请求地址换成了 `http://127.0.0.1:8080/v1`。这里的 `127.0.0.1` 就是本机，`8080` 是模型服务监听的端口。后端会在地址后面拼上 `/chat/completions`。

现在项目用 `config.toml` 选择入口。`third_party` 继续读原来的 `.env` 配置，`llamacpp` 则连本地服务。对我来说，真正花时间的是先弄明白怎样让 `8080` 上有个服务能回答问题。

## 第一坑：下载了 CUDA 包，解压出来只有三个 DLL

GitHub Releases 里那行写的是 `Windows x64 (CUDA 13) - CUDA 13.5 DLLs`。我点了右边，下载解压，打开文件夹一看，三个 `.dll`，连个能执行的文件都没有。

原来这一行里有**两个下载链接**。左边是主程序，里面有 `llama-server.exe`，右边是它需要的 CUDA 运行库。下载对应的两个 ZIP，把运行库放到 `llama-server.exe` 同一目录，才算把程序备齐。

我当时也顺着问了句「CUDA 到底是什么」。现在我的理解是，RTX 5060 是实际干活的硬件，CUDA 是 NVIDIA 提供的软件接口和工具，llama.cpp 通过它安排显卡做模型计算。装好之后，我先跑了：

```powershell
.\llama-server.exe --list-devices
```

看到 `CUDA0: NVIDIA GeForce RTX 5060` 的时候，心里终于有底了。这条命令列完显卡就会退回提示符。之后真正启动模型服务，窗口才会一直开着等请求。

## 第二坑：从自动下载失败，到用绝对路径加载

本来以为接下来一句 `-hf` 就能搞定。它确实能让 llama.cpp 自动从 Hugging Face 下载权重，但我这边连接超时了。日志后面跟着好几条 `failed to load model`，看起来像模型哪里配错了。往前翻，第一条错误其实是 `Could not establish connection`。下载这一步就没过去，后面自然也加载不了。

于是我改成浏览器手动下载两个文件：`Qwen3.5-4B-Q4_K_M.gguf` 是主模型，`mmproj-Qwen3.5-4B-BF16.gguf` 是配套的视觉组件，用来做图片问答。 [模型文件目录](https://huggingface.co/ggml-org/Qwen3.5-4B-GGUF/tree/main)

接着又踩了一个最普通的坑。文件下载到了 `Downloads`，我的 PowerShell 却开在 `Downloads` 下的 llama.cpp 子目录。命令只写了文件名，程序就从当前目录找，两个文件一起报 `No such file or directory`。最后保留原来的文件位置，给 `-m` 和 `--mmproj` 都填上绝对路径，服务就起来了。

这段折腾给我留下的经验很朴素：**先看第一条具体错误，再看最后一条总结。** 前一次是网络连不上，后一次是文件路径写错。两次最后都叫「模型加载失败」，修的却是两件完全不同的事。

## 跑通之后，我才想明白权重和推理的关系

我一开始确实没想明白，只下载一堆参数，模型的「本体」在哪里？

拿 `y = w × x + b` 举例就比较好懂。训练算出了 `w` 和 `b`，但每次给一个新的 `x`，还是要现场算出 `y`。实际模型的计算复杂得多，道理类似。**GGUF 里存着权重和模型相关信息，llama.cpp 里有加载文件、执行计算和生成回答的代码。** 大模型每生成一个 token，都要根据当前上下文再算下一步。

这样也能理解为什么服务窗口一直开着。程序可以把权重留在显存里，空闲时等请求，有人提问才开始处理输入和生成答案。网页关了可以再开，只要 `llama-server` 还在运行就能继续聊。电脑重启之后重开服务就行，权重已经在硬盘上。

还有两个名字是我之前容易混的。`mmproj` 负责让模型用上图片信息，**KV 缓存**则保存生成过程中部分已经算过的注意力结果，方便下一步复用。KV 缓存跟着上下文走，项目写进 PostgreSQL 的历史提问则可以留到后面再检索。这两类「记住」发生在不同地方。

## 为什么先选 4B，以及 vLLM 准备怎么试

我选的是 Qwen3.5-4B，因为我想用中文对话、后面接截图，还要验证模型会不会主动调用 `callback_memory`。显卡只有 8 GB，先用 4 位量化比较现实。我的粗算方式是**参数量乘每个参数占的位数，再除以 8**。约 40 亿参数用 16 位存，理论权重就接近 8 GB，用 4 位大约是 2 GB。实际文件会更大，跑起来还要给视觉组件、上下文缓存和临时计算留空间。因此我先从 **4K 上下文、单并发**开始，留出余量跑通基本流程。

vLLM 准备试同一个基础模型的 **AWQ 4 位版**。它的权重通常是 `.safetensors` 文件，和模型配置、分词器一起放在仓库里。llama.cpp 我这次用 Windows 上的可执行程序跑起来了，vLLM 则计划放到 **WSL2 的 Ubuntu** 里。当前会话查 WSL 时遇到了访问拒绝，所以下一步得先确认 WSL2 里能看到显卡，再看 4B AWQ 在 8 GB 上究竟能不能稳定跑图文和工具调用。这次还没有两套框架的速度或显存对比数据。 [vLLM 安装文档](https://docs.vllm.ai/en/latest/getting_started/installation/gpu/) · [AWQ 候选权重](https://huggingface.co/axteam/Qwen3.5-4B-AWQ-4bit)

## 能对话以后，我最想测的是记忆到底有没有用

现在本地网页能聊天，项目的 `/chat` 也已收到过本地模型的回答。下一步我更想看的是，同一个追问交给本地模型，它会不会真的去查历史。

目前的流程是模型先决定要不要调用 `callback_memory`。触发后，后端用**本轮提问**去搜同一会话里最多三条相似的历史提问，再把结果作为单独的 `tool` 消息交给模型。本轮提问仍然在自己的 `user` 消息里。工具消息让模型知道这段内容从哪里来，至于最终会不会用上，还是得看回答。

一个很实际的例子是，我以前问过「数据库端口是多少」，助手回答「5433」。如果 `5433` 只出现在助手回答里，当前记忆库召回那条问题也找不回端口号。这个例子让我觉得，测 RAG 得拆开看三件事：**工具有没有触发，召回里有没有答案，模型最后有没有用上答案。** 光看终端显示「召回了三条」，很容易以为记忆已经起作用了。

今天最有成就感的时刻很简单：在本地网页打下「你好」，看到它真的回了，然后又让自己的项目接上了同一个服务。折腾完这一轮，我再看到 CUDA、GGUF、端口、工具调用这些词，已经能大概知道出问题该往哪一层找。等 vLLM 跑起来，我想拿同一组截图和历史追问再测一遍，看看换一个推理框架，日常用起来到底有什么差别。
